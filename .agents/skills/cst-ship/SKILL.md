# cst-ship · 交付

## 确定本批范围

读取仓库 AGENTS.md、HANDOFF/README.md 和当前任务的有效交接，确认本批成果、验证结果、源分支、目标 main、PR 和指定清理对象。使用当前对话中已成立的授权，不重复索要；仅询问、引用命令或加载 skill 不授权执行。

用户明确“交付”覆盖已经核清的本批发布、合并、同步和指定对象清理。只推送或只创建 PR 就停在该范围。缺少必须的正式裁定、成果有新变化或对象不明确时，先呈报具体差异和缺口。交付不代替 Freeze、done/close，也不自动开始下一任务。

## 发布与合并

- 完成适用 Verify 和正式申报核对。已有成果核差覆盖的内容不重复审批；不能在交付中夹带新的修复或功能。
- 如果已有对应 PR，先核实仓库、源/目标、源提交、正文和状态。已合并就继续检查同步与清理；结果未知先查询，不能重建 PR 或盲目重试写入。用户只要求推送时不调用会创建 PR 的 publish。
- 确有待发布动作且既有工具接受合法输入时，发布复用仓库已公布的入口。本仓使用 `python3 -B mechanisms/handoff-protocol/github_pr_api.py publish --request <JSON> --root <任务 worktree> --json`，请求按现行帮助填写，放仓外或已忽略暂存。publish 已包含交接准备、申报和发布回读，无需再单独发起一次 handoff。不绕过其归档、身份或条件检查。
- 合并前再次核对本批源提交和适用检查。使用已有 GitHub 工具，本机优先 `gh-axi`；合并操作绑定已核源 SHA，采用 merge commit 保留交接历史。检查失败、保护不满足或源提交变化时停止，不自动批准、不 bypass、不 squash/rebase。
- 合并后读取 PR 的实际 merged 状态、源 SHA 和合并提交，并核实成果进入目标。PR 关闭或源分支消失不能代替合并证明。

## 同步与清理

确认保留的 main checkout 身份、工作区状态和当前授权，fetch 后仅用快进同步；发生分叉或未知改动时保留现场，不 reset/rebase。已确认本批成果进入本地 main 的，继续核清理，不因重复调用重新发布或合并。

对拟清理的指定对象使用既有 `handoff_workflow.py check-cleanup --task <id> --source-sha <交接 H> --root <保留入口> --json`，并核实际平台合并与唯一材料。该命令只检查，不删除。tracked、untracked、ignored 或仓外唯一材料未保全时保留；备份失败不得删除。

当前会话或其他活动会话仍依赖源 worktree，或无法确认是否依赖时，保留该目录及其本地分支并说明原因。不为了清理迁移宿主、关闭会话或另建执行器。

具备安全条件时，只处理本批已授权对象：远端源删除绑定预期源 SHA；本地 worktree 不强制删除，本地分支只用 `git branch -d`；只处理本批失效 tracking 引用，不全仓 prune。删除前再次核对路径、注册和源提交；对象变化或无法确认来源时停止。

## 中断与结果

用户取消就停止后续写入。明确“继续交付”时，先读原交接，再核 Git、PR 和材料现场，跳过已有可靠完成证据的动作。缺原发布请求且既有工具无法恢复时，报告缺失输入，不编造请求或使用不存在的恢复命令。同批范围仍明确时沿用原授权，范围变了先核新差异。

最终报告 PR 链接、合并结果、本地同步结果、已清理与保留对象，以及具体阻塞。只发布完成就称发布完成；工作区保留时明确清理未完成。进度与跨会话材料沿仓库既有机制保存；不新建交付状态文件，不在 main 补完成收据或为收据再开 PR。

现有交接里的历史建议不能覆盖当前已核实事实；发现已完成的合并或清理建议时说明其已过时，不重复执行，也不改写旧记录。下一业务任务只给有依据的建议，不自动开工。
