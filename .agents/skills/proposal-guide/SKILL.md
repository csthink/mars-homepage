# proposal 引导（proposal-guide）

> 中立能力正本条目（布局权威 §5.2 落点；引导规则的正本 = 本文件自身，模板 = `mechanisms/artifact-templates/proposal.template.md`；proposal-template 设计正本已随减重第 5 步退役）。
> 本条目只承载能力语义：流程、问题、格式、禁则。它约束执行行为，不新设记录文法或机械看守。
> 执行本条目的动作只有三类：在本对话中向用户提问、在本对话中输出、读取仓内文件。本条目不写文件。

## 0. 中立约束

- 不以任何一家 Agent 的专有工具、子代理、命令或会话控制为必经步骤。
- 事实与决定分离：产品定义中的事实（同类产品与相邻产品、既有资料、仓内是否已有 proposal）由你用自身可用手段查证——具备子代理能力时可派发子代理调研，不具备时用对话内手段；查不到即如实标「未知」并继续，不把查证义务推给用户，不用未查证的事实冒充已知。决定恒交用户。查证所得事实进状态块「来源」。
- 起草情境区分新建产品与存量项目。存量项目的已有行为与文档由可查资料支持，并由用户确认其产品含义；查证可以形成事实材料，不可替用户补故事、把当前代码倒写为原始需求或伪造过去的评审/定稿。沿用同一模板和确认流程，输出仍只是候选，不自动取得产品来源权威。
- 对话中断后凭最后一个状态块（§2）从任一轮继续。

## 1. 预备交互（不计入流程轮、不带状态块）

流程开始前只做一件事：向用户索取会话标识，形态 `<日期>·<产品名>·<执行者>`（例 `2026-09-02·SideQuest·mars`）。用户给出后流程才开始；缺失则不进入流程。第一个流程轮的回复即带首个状态块，其 `SRC-01` 已含该标识。

## 2. 状态块（每个流程轮回复末尾必出，累计承载全部工作态）

```text
[proposal-guide 状态]
阶段：发散 | 收敛 | 渲染
故事清单：
- US-01 作为<用户>，在<情境>，我想<动作>，以便<结果>；问题根因：<一句>
定位候选：
- PC-A <一句定位>；最强反对理由：<一句>
已定：
- D-01 <已由用户拍板的决定>
未定：<收敛段写当前前沿问题编号，如 Q3、Q4；发散段写「发散段第 n 层」或「发散段扩散一」「发散段扩散二」>
来源：
- SRC-01 对话记录 <会话标识>；持久化义务：定稿前由用户落为仓内固定身份证据，其路径与 SHA-256 记于快照之外的 provenance 锚；作用：全部故事与决定的直接来源
```

- 每轮输出完整清单，不是本轮增量。四清单各一行一条；编号 `US-NN` / `PC-X` / `D-NN` / `SRC-NN` 整段对话内稳定、不复用；合并或撤回的条目保留原行并在行尾标 `（撤回）`。
- 「来源」从第一个流程轮起累计；`SRC-01` 恒为本次对话记录，自始至终只写会话标识与持久化义务，不写摘要；用户提供的材料、你查证的外部事实各占一条（稳定身份；可得时的不可变 revision 或内容摘要；作用）。
- 状态块是工作态，不进入产出的 proposal。

## 3. 发散段（每轮只问一个问题）

**第一层 · 情境提问（产出用户故事）**。对用户的每个念头依次问：这个人是谁；他此刻在做什么事；他今天用什么替代做法；该替代做法的代价是什么；做成了他怎么知道。五问走完记为一条 `US-NN`。用户给功能名而非情境时追问「谁在什么时候会用到它」，不把功能名记为故事。

问题模板：
- 「先从一个具体的人开始。这个人是谁？」
- 「他此刻在做什么事？」
- 「他今天用什么替代做法？」
- 「该替代做法的代价是什么？」
- 「做成了他怎么知道？」

**第二层 · 根因追问**。对每条故事的问题点追问「为什么」两到三次，直到落到一个不依赖本产品也成立的事实，记为该故事的「问题根因」。

**第三层 · 反向划界**。至少问一次「谁不是用户？」与「哪种情境你明确不管？」，答案记入已定项。

**扩散一 · 定位候选**。故事达到三条后，主动给出至少三个互不相同的产品定位候选 `PC-X`（例如工具 / 服务 / 平台三种取向，或面向不同用户群），每个候选配一句最强反对理由，请用户挑选、合并或改写。用户未选前不进收敛。

**扩散二 · 失败原因预设分析**（先假定产品已失败，再由用户列出最可能的原因）。至少问一次「一年后产品失败了，最可能的原因是什么？」，答案按三类记入已定项：必须现在定的（R1 素材）、同类失效应一并封住的（R2 素材）、可接受的（R3 素材）。

## 4. 发散到收敛的切换（双轨）

- 机械条件：故事不少于五条（撤回者不计）、覆盖至少两类用户、用户已选定一个定位候选。三条同时满足时提议进入收敛，用户确认后切换。
- 用户可随时宣布进入收敛：先逐条列出尚未满足的机械条件与其后果（哪一节可能写薄），然后照办，不拒绝、不反复劝阻。
- 收敛段发现故事缺口时可临时回发散段补一条，补完即回收敛；状态块「阶段」随之切换。

## 5. 收敛段（决定树 + 分轮前沿）

决定树（六节依赖顺序，固定）：

```text
P1 产品是什么（定位 + 是什么 / 不是什么）
└─ P2 目标用户与问题（由故事清单与问题根因导出）
   └─ P3 MVP 边界（每条故事三选一：In / Out / 不决定）
      ├─ P4 MVP 成功条件（每条 In 故事至少派生一条，写结果对象与可观察结果）
      ├─ P5 本提案不决定的事（每条「不决定」故事写明下游承载方；无则写「无」）
      └─ P6 反思（R1 / R2 / R3 由失败原因预设分析素材与 P3 取舍导出；R3 无残留写「无」）
```

- 每轮把「前置节已定」的全部问题一次问完；同一轮内不得有互相依赖的问题，依赖本轮未答题的归下一轮。第 1 轮 = P1；第 2 轮 = P2；第 3 轮 = P3；第 4 轮 = P4、P5、P6（三者只依赖 P3）。
- 轮次格式：

```text
Q<n> · <节名> · <问题标题>
<问题正文，可含选项>
建议：<你的建议答案>（依据：US-xx / PC-x / D-xx）
```

- 映射规则：六节每一条内容都能指回故事编号、候选编号或已定项；无法指回的标注「无依据，待用户确认」。P3 的 Out of Scope 不得写「后续再定」，此类条目归 P5 并写承载方。
- 前沿空即收敛完成：逐节复述最终内容，取得用户明确确认后才进入渲染。

## 6. 渲染

1. 读取 `mechanisms/artifact-templates/proposal.template.md`（相对仓根）。
2. 用用户给出的产品名替换唯一占位 `<产品名>`；产品名不得含换行、`<`、`>` 与首尾空白。
3. 删除全部 `<!-- template:guide … -->` 注释块。
4. 在「目标用户与问题」与「MVP 边界」之间插入扩展 H2 `## 用户故事`：状态块故事清单最终版，每条一行无序列表（编号、故事句、问题根因；撤回条目不入）；不承载治理状态或对话过程叙事。
5. 六个核心节与三个 R 节按收敛结果填入；全文 H2 不编号。
6. 渲染前看守（逐条核并在对话中报告；任一项不满足即不得报告为模板合规）：
   - 结构面：H1 恰一行；页首逐字等于模板页首且 `Depends on` 为 `无`、subject 为 `proposal`；六个核心 H2 与三个 R 节各恰一次且序合规；`## 用户故事` 恰一次且不与核心标题碰撞；无注释残留、无 `<产品名>` 残留。
   - 语义最低承载面：P1 含产品定位、交付形态与「是什么 / 不是什么」边界；P2 含目标用户、问题与产品目标，不是功能名清单；P3 In 与 Out 两面在场，Out 中无「后续再定」；P4 每条给出结果对象与可观察结果；P5 每项写承载方，无留白时写「无」；R1 说明不现在定就无法安全推进的内容；R2 说明同类失效如何一并封住；R3 分级列残留，无残留写「无」。
   - 禁入面：全文不含 Status、评审、定稿、下一步、「尚未」类当前态缓存；扩展节不含对话过程叙事。
   - 用户手动提前收敛导致语义面不满足时，仍可应用户要求输出候选，但须逐项列出未满足项并明确报告「该候选尚不满足 proposal 模板语义最低承载，不得作为合规候选送审」。
7. 产出形态 = 在对话内输出完整候选文本（一个 Markdown 代码块）与 §7 来源清单，并附落点说明：候选的规格链槽位由所在仓布局权威派生（本布局为 `sdd/proposal.md`），槽位已有现行 proposal 时新候选走 proposal amendment。不写入任何文件、不执行实例区落位；入仓、送审、定稿与落位由用户或其后续流程执行。输出候选与来源清单的这条回复即对话记录快照的最后一条消息。

## 7. 来源清单（渲染后必出）

内容 = 状态块「来源」字段最终版（含撤回沿革）。随后逐字提示两项定稿前提：

1. 把对话记录快照（自预备交互起、至输出候选与来源清单的回复为止，含全部状态块）持久化为仓内固定身份证据（路径 + SHA-256）。
2. 在快照之外建立 provenance 锚，形态严格取二者之一：Owner Decisions 直接记录本来源清单并记录快照的路径与 SHA-256；或由评审任务书 / founding provenance 记录 / lineage 记录承载本来源清单与快照身份，再由 Owner Decisions 记录该承载件的路径与 SHA-256。Owner Decisions 不得直接指向快照。

两项缺一即零来源、不得定稿。

## 8. 禁则与停止规则

- 禁引导式提问：不在问题里预埋答案；候选定位由你给出但选择权在用户。
- 禁替用户补故事：故事句必须来自用户回答，你只做结构化转写并回读确认。
- 禁把功能名当问题：P2 出现功能名而无情境与代价时不得进收敛。
- 禁写治理状态：实例正文与扩展节不得出现评审、定稿、amendment、轮次、「待补」类内容。
- 停止规则：用户在发散段明确表示不再有新故事且机械条件不满足时，列出后果后按用户决定；用户拒绝确认收敛结果时回到前沿重问，不强推渲染；产品名不合法时不渲染。
- 问题总量不设上限，但每一个流程轮都须报告状态块，用户随时可据其判断是否收束。
